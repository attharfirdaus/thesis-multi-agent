# Running the thesis batch job without a VM

Scope: lecturer uploads a class batch of 30–100 submissions. Per submission the FastAPI + LangGraph pipeline makes several sequential LLM calls (≈10–60 s), so a whole batch runs 10–60 minutes. LangGraph checkpoints into Postgres, so resumability is already built into the pipeline — what's missing is *who calls the pipeline, how many times, for how long, and what happens when that caller dies mid-batch*. A single HTTP request cannot hold a 60-minute job open reliably on any platform below, so every pattern is really "what triggers/hosts the per-submission (or per-task) unit of work, and how does it survive restarts."

All facts below were fetched live today (2026-10-07) from primary vendor docs/pricing pages; each cell cites its source URL. Owner constraint: **no VM** (no SSH, no OS patching, no firewall/reverse-proxy work) — this rules out Fly.io Machines and self-hosted Temporal/queue workers even where otherwise attractive.

**Conclusion:** no free-tier HTTP platform reliably holds a request open 10–60 minutes (Cloud Run's 60-min service ceiling is the single outlier, and it is still one request = one monolithic unprocessed-failure unit with no per-submission retry). None can process a 30–100-submission batch "inside one long request" and still offer per-submission retry/resumability — every workable pattern above decomposes the batch into independently-retried units (one Lambda/Cloud Run Jobs task per submission, or one GitHub Actions job polling a table), never a single request holding the whole batch.

## Patterns that actually satisfy "30–100 submissions, resumable, $0, no VM"

### 1. GitHub Actions scheduled/dispatched workflow as the batch runner
The backend writes 30–100 job-table rows, then either pushes a `workflow_dispatch` via the GitHub API immediately or lets a `schedule:` cron (min 5-min granularity) pick them up. The job itself is a normal Python process with up to **6 hours** of runtime — far more than the 10–60 min needed — polling the Postgres job table, claiming rows with `UPDATE ... WHERE status='pending' RETURNING` (idempotent claim), running the LangGraph pipeline per submission, and writing per-submission status back to Postgres for the UI to read. LangGraph's own Postgres checkpointing gives resumability if the job is cancelled or the runner crashes mid-run.
**Failure mode:** scheduled triggers are best-effort and "can be delayed during periods of high loads... some queued jobs may be dropped" (no numeric SLA published) — a time-sensitive workflow_dispatch call from the backend avoids this, but then the backend needs a GitHub PAT/App token as a secret. A public repo keeps minutes unlimited but is unacceptable if the repo must stay private for student-data code; then the 2,000 free min/month cap applies (plenty for occasional batches, tight if run daily). The 60-day auto-disable on inactive **public** repos needs a watchdog if runs are infrequent.

### 2. Cloud Run Jobs, one task per submission
The backend calls the Cloud Run Jobs REST `run` API with `--tasks=N` (N = batch size) when a batch is submitted. Each task is one submission's pipeline run, independently retried up to `--max-retries` (0–10) without affecting siblings, and the job as a whole has **no execution-level timeout** — it just runs until every task finishes or fails out. Per-submission status surfaces through Postgres (the app writes status itself; Cloud Run gives no native per-task progress API beyond execution logs). This stays inside the 240,000 vCPU-s/450,000 GiB-s free tier by a wide margin for a 100-task, ~30s-each batch.
**Failure mode:** platform maintenance can migrate a running task to a new machine mid-execution (breaking any open VPC connection, requiring reconnect), and Cloud Run Jobs' retry counter is per-task, not whole-batch — a submission that exhausts its retries marks the *job* execution failed even though other tasks succeeded, so the UI must read task-level status, not job-level status, to show partial success. Billing requires a GCP billing account attached (card-on-file) even though usage stays at $0.

### 3. Cloudflare Workflows (Free plan) as the durable orchestrator
A Worker-based Workflow orchestrates the batch: one Workflow instance per submission (or one instance iterating the batch with a step per submission), each `step.do()` automatically checkpointed and retried (up to 10,000 retries/step) without rerunning prior steps. Crash/eviction resumes from the **last completed step** — this is the strongest native resumability of any $0 pattern that isn't AWS Step Functions. Free plan gives 100,000 executions/day and 1,024 steps/workflow, comfortably covering 30–100 submissions.
**Failure mode:** the Workers Free plan caps **CPU time at 10 ms per step** — fine for steps that are mostly `await fetch()` to an LLM provider (wait time is free), but any real JSON assembly/parsing/branching inside a step risks `exceededCpu` errors; a pipeline with non-trivial per-step logic will likely need the Paid plan ($5/mo minimum) to raise the cap to 30s–5min, which breaks the strict $0 target.
